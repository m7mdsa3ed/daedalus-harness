# Product videos with video-mcp

You are not generating a video. You are **editing a document** (`storyboard.json`) and asking the
tools to **build** it. Never try to get it right in one shot: draft, look, say what you see, let
the user steer, repeat. A draft is cheap and cached; that is the point.

## The loop

1. `video_providers` once, to see what is configured. Narration with no TTS configured is
   **silent** (a real silent track of the right length). That is fine for the first drafts: pacing
   and picture get agreed before any voice is paid for. Say so to the user; do not configure keys
   yourself. If its `remotion` block says not installed, tell the user the install line and stop:
   the video cannot be previewed or exported without it (Remotion is free for individuals and small
   teams, paid above that; say so, never install it yourself).
2. `video_init {name, title, baseUrl}` (or `video_import_recorder` if the user has a Chrome
   DevTools Recorder export). `name` is lowercase letters, digits and hyphens.
3. Open `.daedalus/videos/<name>/storyboard.json` and **write the steps with your file tools**.
4. `video_build {name}`. It captures the flow and narrates it (no render), writes the assets into
   `studio/` and starts Remotion Studio. It returns `{jobId}` immediately; poll `video_job {jobId}`
   every few seconds until `done` or `failed`. A failure message says what to fix. The result holds
   `studio.url`.
5. Give the user the Studio URL: the video plays there live. Also `video_review {name}` for
   yourself (about 30 s): the contact sheet comes back as an image, one still per scene, plus a
   report. It needs no mp4.
6. Tell the user, briefly, what you saw and what you changed. Ask what to change. Go to 3.
7. `video_export {name}` writes a **draft** mp4. When the user is happy, `video_export {name,
   quality: "final"}`, only after they approve. Then `video_publish` **only if they ask** for it in
   the Files library.

`video_export` takes `scene: <stepId>` (that step's card and clip) or `frames: "a-b"` for a quick
fragment, written to `<name>-<quality>-part.mp4`; it is never published. Poll `video_job` for exports
too. `video_studio {name, action}` starts, stops or checks Studio (a build already started it).

Do **not** export a final to check your work. Do **not** publish after every export.

### Two kinds of edit, two prices

- **Storyboard edits** (what a step says or does, adding/removing a step) go through `video_build`:
  narration is cached per line, the browser flow re-records.
- **Composition edits are free.** Cards, captions, zoom easing, colours, the progress bar and sounds
  live in the Remotion project: edit `.daedalus/videos/<name>/studio/src/` (React/TSX) or
  `studio/props.json` and Studio hot-reloads. No build, no tokens spent on TTS. The person may have
  edited the composition already; read it before changing it, and never `resetStudio` without being
  asked (it discards their edits). `props.json` and `studio/public/` are regenerated by every build:
  edit the storyboard, not those.

## Writing a storyboard

```json
{
  "version": 1,
  "title": "Tasks demo",
  "baseUrl": "http://localhost:5173",
  "steps": [
    { "id": "open", "say": "Here is the task list.", "do": { "action": "goto", "url": "/" } },
    { "id": "new", "say": "Press New task to start.", "do": { "action": "click", "selector": "#new" }, "zoom": true },
    { "id": "title", "say": "Type a title.", "do": { "action": "fill", "selector": "#title", "value": "Ship it" },
      "overlay": { "text": "Just type", "position": "bottom" } }
  ]
}
```

- **One step = one beat the viewer takes in**: a short sentence of narration and the one or two
  actions that happen under it. Narration is read at about 3 words/second; keep a line to a sentence.
- `do` is one action or an array. Two shapes work, pick one per step:
  - Playwright style: `goto`, `click`, `fill`, `type`, `press`, `hover`, `wait {ms}`, `scroll`.
    `selector` is a Playwright locator string (`#id`, `text=Save`, `role=button[name="Save"i]`).
    Spelling mistakes are an error, which is good.
  - Chrome Recorder style (`{"type":"click","selectors":[["aria/Save"]]}`) as exported.
- Relative urls resolve against `baseUrl`. The first step should navigate.
- `hold` is extra milliseconds after the narration ends (default 400). `voice` overrides the voice.
- `id` is `[a-z0-9_-]+`, unique. Use meaningful ids: the user will say "the checkout step".
- Any change to a narration line re-records the flow (its audio length is part of the capture key),
  so word it before the first build; an `overlay` edit does not. A flow that creates data replays it each time.

## Reading the contact sheet and report

The sheet has one cell per scene (a clip's mid-frame; the intro and chapter cards are one cell each)
labelled with the step id and start-end **on the video's own clock, which the cards shift**, with the
narration under it. Check, in this order:

1. **Is the right screen showing** in each frame? A frame still on the previous page means the
   action did not run: look for a warning on that step.
2. **Warnings** in `report.warnings` / `report.steps[].warnings`:
   - "selector not found" or an action timeout: the selector is wrong or the element is not there
     yet. Fix the selector, or add a `{"action":"wait","ms":800}` or an earlier step that opens it.
   - "audio is longer than the step": the voice will be cut or overlap. Shorten `say` or raise `hold`.
   - "zoom requested but no target": zoom has nothing to frame. Give `zoom` a `selector`.
   - "blank first frame": the page had not painted. Add a `wait` to the first step.
3. **Pacing**: compare `audioMs` with `stepMs`. A step much longer than its audio is dead air; a
   step barely longer is rushed.

Say what you found in plain words ("step 3 shows the old page; the Save selector did not match, I
changed it") and rebuild. Do not hand the user the raw JSON.

## Mapping feedback to edits

| The user says | You do |
| --- | --- |
| "step 3 is too fast" / "let me read it" | raise that step's `hold` (e.g. 1500) or lengthen `say`; not other steps |
| "too slow" / "drags" | shorten `say`, lower `hold` |
| "zoom into the button" | `"zoom": {"selector": "#new", "scale": 1.8}` on that step (`true` frames the element the step acted on) |
| "zoom out" / "too much zoom" | remove `zoom`, or lower `scale` (1-4) |
| "add a step between X and Y" | insert an object with a new unique `id` in `steps` at that position; the other narrations stay cached |
| "drop the intro" | delete the step. Do not renumber ids |
| "say it differently" | edit `say` only |
| "add a title card before this part" | `"chapter": "Title"` on that step (a 1.8 s card shows before it) |
| "add a label that says ..." | `"overlay": {"text": "...", "position": "top"}` |
| "change the voice" | set `voice` on the step or the storyboard (voice ids belong to the TTS provider) |
| "that part is perfect, don't touch it" | `"locked": true` on the step. A build fails if a locked step is edited; remove `locked` first if the user changes their mind |
| "it is not clicking the right thing" | fix the `selector`; check the sheet's frame for that step |
| "use a recording I already have" | `"providers": {"capture": "file"}`, `"file": "rec.mp4"` (relative to the video folder), `"at": <ms>` on each step (steps without `at` are spread evenly and warned as inferred) |

Edit **only** the step the user is talking about. Changing other steps invalidates caches and
re-records for nothing.

## Builds, caching and cost

- Unchanged narration is reused from cache; the browser flow is reused when no step's actions or
  durations changed. The build report says `hit`/`miss` per step. Changing what a step *does*, or
  adding/removing a step, re-records the whole flow (about the length of the video); that is the cost
  of browser state being sequential. Per-step capture does not exist yet.
- `force: ["capture"]` when the app under test changed but the storyboard did not;
  `force: ["tts"]` only if the user asks (it costs money with a paid voice).
- Only one build and one export per video run at a time.

## Publishing

`video_publish {name, quality}` uploads `out/<name>-<quality>.mp4` (from `video_export`) to the harness
Files library under `Videos/<name>`. Missing file: run `video_export` first.
- The library caps files at **25 MB**. If an export is over, say so and offer a draft, a shorter
  video, or a smaller `viewport` in the storyboard. Do not retry blindly.
- Without the harness (standalone) it returns the local path; tell the user where the file is.
- Publish only when the user accepts a version and asks for the file, and tell them the folder and name.

## Don'ts

- Do not run Playwright, ffmpeg, Remotion or a browser yourself; the tools do it. Never start Studio by
  hand (`video_studio`), and never widen `VIDEO_STUDIO_HOST`: Studio can write files and render, and
  it is loopback-only on purpose.
- Do not put API keys in the storyboard or in chat. TTS keys are server environment variables.
- Do not hand-edit anything under `.cache/` or `out/`, or `studio/public/`.
- Do not describe the video from the storyboard; describe it from the contact sheet.
